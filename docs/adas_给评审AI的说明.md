# 给评审 AI 的说明

## 0. 一句话

这是一个**车载 ADAS 可视化**项目：把行车记录仪视频跑成一个"类特斯拉"的
实时画面 —— 目标检测 + 跟踪 + 本车道中心线 + 一块数据仪表盘。
主要的原创工作在**车道几何**这一块，而那一块的结论**大半是负面的**，
负面结论都写下来了，希望被挑错。

---

## 1. 任务是怎么来的（用户原话，逐字）

> 「我把总方案和子方案都给你，你看看怎么实现最为合理，反正最后我们需要
> 呈现出来的是一个类似 adas 的效果，比如特斯拉的智能驾驶的那种。」

> 「看看现有工程中，车道线的处理是怎么做的，包括 rtl 和算法，我需要知道
> 现在能做到哪一步。如果你觉得当前车道线识别方案不够好，你可以提出一个
> 更好的方案，因为我需要的是，在最后可以把车道线识别结果叠加到 adas 画面中。」

> 「那就不需要自动转向判定了，不要这个呈现，只要那个线条的判断趋势就行，
> 这样你把这个做成一个本地脚本或者本地网页，要求我直接把新的视频拖进去
> 就能进行你视频里呈现的那样的实时检测。」

## 2. 硬件与部署背景（约束）

* 车上链路：**盘古 50（PGL50H）FPGA** 负责相机与显示，推 720P 图像给
  **鲁班猫 1 金手指（Rockchip RK3566，4×Cortex-A55，4GB）**做推理。
* 现有 FPGA 侧的车道叠加 RTL（`lane_draw.v`）**语义只有"左右各画一条直线"**，
  端口里没有 score / offset / 无效原因 / 曲率 —— 本项目的输出口径是按
  `PGL50H子方案.md` 的冻结字段（`center_offset_px` / `curvature_px_inv` /
  `confidence_score` / `lane_status` / `invalid_reason`）对齐的。
* 因此画面上的所有数字都遵守一条纪律：**校准前不称概率、像素量不冒充米制量、
  没把握就写 `unavailable` + 原因码**。

## 4. 请重点评审这几件事

按重要性排序。每一条都请**给具体做法**，不要只说"可以更好"。

1. **输出参数化还有没有更好的？**
   现在是：锚点（参考行处的 u）用 64 箱 softmax **取期望**解码，
   形状用二次基 `du(t) = s·t + q·t²`（`t = (v − y_ref)/L`）。
   实测残差 0.01 px（解析重建）。有没有更合理的头部？
   （试过 7 个自由 u 直接回归、纯 64 箱分类，都更差。）

2. **"幅度被压扁"的根因诊断对不对？**
   实测：输出范围 −59~+138 px，真值 −220~+349 px；
   右尾回归斜率 k 从 0.68 提到 1.10（V3 之后）；
   留出片段上整体 r=+0.482、std 比 0.413。
   我的结论是：**296 个样本撑不起这个条件分布，压向条件均值是贝叶斯最优解，
   不是损失函数形状问题**（换分类头 + CE 更差，佐证）。
   这个诊断成立吗？如果成立，正确的处方是加数据还是换中间表示？

3. **置信度的标定是不是在自欺？**
   现在用 `log(|误差|+1) ~ |anchor| + |s|` 拟合，按**留一整个片段**评估
   （rho +0.328）。但拟合样本是 **LOSO 误差**（模型没见过那一段），
   部署用的是**见过全部 296 帧**的全量模型 —— 两者不匹配，
   已经踩过一次"外推爆炸把一个正确答案判成不可信"的坑。
   现在的兜法是按拟合集分位数截断。**有没有更干净的做法？**
   另外它的结构性盲区是：**自报幅度看不出系统性符号错误**
   （十分位第一档预期最准、实际误差 43.9 px）。这个盲区能补吗？

   **在问之前我已经撞死了三条路，请不要再提这三条**（细节见路线文档 §10.2）：
   * 用检测框挖"前车挡住参考行"的负样本 —— 前 100 秒 3000 帧 **0 命中**。
     原因是参考行在**车前约 4.1 m**，要被别的车盖住得贴到前保险杠，
     正常行驶不会发生。**我想错了失效模式。**
   * "采样带里没有漆线 ⇒ 不可信" —— 漆线覆盖率与 |误差| 的
     Spearman 只有 **−0.011**（中心带 −0.013），无信号。
   * 亮度 / 梯度 / 车辆数 / 最大车宽 —— −0.062 / −0.100 / −0.040 / −0.060，全废。

   唯一有信号的是**模型自己报的那个数有多大**（`|anchor|` rho +0.359，
   `|s|` +0.319），而原来那个 logit 是 **−0.138（反的）**。
   所以现在这条路本质上是"**用输出幅度当不确定度**"，
   它系统性地看不见"输出方向错了"。**有没有第四种特征来源？**

4. **评估方法有没有漏洞？**
   * 296 帧 / 8 个路段，**留一整个路段**交叉验证（LOSO），9 折。
   * 单次 LOSO 的逐折数字有 **±5 px 量级**的运行间噪声（同配置跑两遍量过）。
   * 已知混淆项：**"街道数变多"与"帧数变多"分不开**（1 街 22 帧 vs 8 街 280 帧）。
   * 全部标注**只有正样本**（每一帧都有本车道中心线），
     所以"有效性头"退化成常数（已修：改用标定的预期误差）。
   有没有更省数据量的评估协议？

5. **代码结构。**
   `adas_dash.py` 里定义了 `AdasPipeline`，`adas_demo.py` 里是检测 + 自写
   ByteTrack + 各种绘制原语，`adas_live.py`（本地网页）与 `adas_dash.py`
   **共用同一个 `AdasPipeline`**。这样分合适吗？
   有没有更该抽出来的边界？

6. **我漏掉的路径。**
   目标是"像特斯拉"。现在画面里：目标框 + 轨迹拖尾 + 运动趋势箭头 +
   本车道中心线 + 六张数据卡。
   **有没有比"继续抠车道回归精度"更划算的方向？**
   （我自己的判断是：车道实例分割换掉当前回归头，见路线文档 §7。）

## 5. 三条明确判死的路（**别建议重走**）

1. **从 33 ms 帧差里抠自车偏航角速度** —— 三次估计器全部判死。
   最根本的原因：真实转弯 5–8 deg/s 只造成 0.17–0.27 °/帧的信号，
   而 LK 的 0.1–0.2 px 定位噪声在约 450 px 力臂上折算约 0.35 °/帧，
   **信噪比 < 1**。偏航角速度是**状态量**，不是能从帧差里抠出来的观测量。
   （细节见路线文档 §6.3）

2. **单目 IPM 自标定相机高度 `cam_h`** —— 数学上无解。
   `x_metric = (u−cx)·cam_h/(v−cy)`，`f` 直接约掉，
   所以"相机高"与"横向米制尺度"**是同一个自由度**。
   我曾在图像上搜 `(cam_h, y_horizon)` 的栅格，那不是"没搜到"，是**没有唯一解**。
   **必须靠外部信息定标。**

3. **在路口用车道几何判方向** —— 物证见 `shots/07_intersection_no_laneline.jpg`：
   路口一帧里一根车道线都没有，而 Hough 会在斑马线/建筑边缘上拟合出
   30 deg/s 的"偏航速率"假信号。**车道几何是 fair-weather 信号。**

## 7. 一个正在讨论中的新方向：双目

用户刚提出"我们可以进行双目识别了"，并问了一个很具体的问题：

> 如果双目视频里两路画面完全一样（没有任何角度差），是否本质上没有区别？

我的回答写在下面，**希望评审也看一眼这个判断对不对**：

* 如果两路**逐像素相同**，那么视差恒为 0 ⇒ `Z = f·B/d` 发散 ⇒
  得不到任何米制深度。此时双目 = 单目，而且更糟（2× 算力，0 收益）。
  **它甚至不解决第 5.2 条那个尺度模糊** —— 尺度模糊要的是 `B ≠ 0`
  且 `B` 已知。
* 但"看起来一样"是**双目的正常状态**，不是故障：`d = f·B/Z`。
  f=914 px、B=0.12 m 时，10 m 处视差 **11 px**、50 m 处 **2.2 px** ——
  都是可以亚像素匹配的量级。"画面看起来没差别"不等于"没有视差"。
* **双目真正能解掉本项目最大的那个死结**：已知 `B` 时，
  路面在某一行的视差给出 `Z_road = f·B/d`，`cam_h` 随之确定 ——
  这正是单目无解的那个自由度。
* 但先决条件是**外参标定**（相对位姿 R,t）。没有标定就不能做极线校正，
  只能做二维搜索，既慢又不稳。
* 一个便宜的判定方法：取一对帧跑 `cv2.StereoSGBM`，
  看视差图是不是恒 0 或纯噪声；或对左右图做相位相关，
  看峰值位移是不是 0。
