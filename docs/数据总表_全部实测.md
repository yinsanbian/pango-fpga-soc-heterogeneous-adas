## 2 · 部署精度：FP32 vs INT8

### 2.1 640×640（正式上线档）

| 模型 | mAP@0.5 | mAP@0.5:0.95 | 体积 | 单帧(ms) |
|---|---|---|---|---|
| FP32 基线 | **0.6627** | 0.4809 | 11.52 MB | 29.4 |
| INT8 (QDQ) | **0.6875** | 0.4971 | 3.17 MB | 66.2 |

保留比例 **103.74%**（门槛 95%），裁决：**直接上线**。

> ⚠ **INT8 比 FP32 精度还高 2.48 个点，这不是"量化提升了模型"，是量化噪声落在了评测的抖动范围内。** 129 张 val 上 mAP 的置信区间大约 ±3 个点，2.48 的"提升"和 −1 的"下降"在统计上分不开。正确的说法是：**量化没有造成可测的精度损失**，不是"量化让模型更准"。

> 板端 RK3568 同模型（INT8 RKNN）的实测在 §10：单路前向 total 均值 **47.44 ms/帧**（n=100，文件源，含前后处理，不含 JPEG/UDP）。它与本表 x86 CPU 的 66.2 ms 不是同一后端/前后处理，不能直接比较；x86 的 ms 列仍然只能说明"在 CPU 上测过"。

### 2.2 320×320（轻量档）

| 模型 | mAP@0.5 | mAP@0.5:0.95 | 体积 | 单帧(ms) |
|---|---|---|---|---|
| FP32 基线 | **0.5276** | 0.3174 | 11.52 MB | 13.4 |
| INT8 (QDQ) | **0.5019** | 0.2954 | 3.17 MB | 28.9 |

保留比例 **95.13%**（门槛 95%），**刚刚过线** —— 只比门槛高 0.13 个百分点。取证时如果换一批 val 图，很可能掉到门槛以下。**这条要写明：320 档的量化是"勉强通过"，不是"稳定通过"。**

| motorcycle | 19 | 0.5061 | 0.5754 | 0.7481 | 0.7637 |

> `bus` 那格的两个数来自不同报告（`report_full320.md` 写 0.4291，`resolution_compare.md` 写 0.6522），**两份报告不一致**。以 `report_full320.md`（直接对应证据 JSON）的 **0.4291** 为准；`resolution_compare.md` 那格疑似抄错。**这是我自己生成文档时留下的不一致，已在此标注。**

**量化的真实影响面**：大目标（car/truck/bus）几乎无损（<2 个点），小目标（traffic light 掉 4.4、traffic sign 掉 2.2）损失最大。这与"量化误差对小目标的分辨率影响更大"的常识一致。

### 2.4 关于"INT8 在 CPU 上更慢"这件事

单帧耗时 INT8 是 FP32 的 **2.25 倍**（640 档 66.2 vs 29.4 ms）。**这不是 bug，也不是量化失败。**

原因：ONNX QDQ 格式在 x86 CPU 上如果没有 VNNI/AMX 优化 kernel，onnxruntime 会走"每层反量化回 FP32 计算再重新量化"的路径，中间的 `QuantizeLinear`/`DequantizeLinear` 是纯额外开销。

**所以这张表里的 ms 列不能用来评价量化效果**，只能用来表明"我在 CPU 上测过"。量化的真实收益（体积 12.08→3.17 MB、内存带宽需求降 3.8 倍）只有在 **RK3568 NPU** 上才能体现。RK3568 板端实测见 §10（UVC 2026-11-01 + 文件源 NPU 2026-11-03）；x86 的 ms 列仍然不能替代 NPU 数字。

## 3 · 模型文件清单（含 sha256 前 16 位）

### 3.1 交通目标检测（六输出 split 格式，opset 17）

| 文件 | 字节 | MB | sha256[0:16] |
|---|---|---|---|
| `traffic9_split6_320.onnx` | 12,077,567 | 11.52 | `409ad3b88852eaae` |
| `traffic9_split6_320_int8qdq.onnx` | 3,325,608 | 3.17 | `fa06cbddd7aaad8e` |
| `traffic9_split6_640.onnx` | 12,077,567 | 11.52 | `ced3582a2caafa9d` |
| `traffic9_split6_640_int8qdq.onnx` | 3,325,646 | 3.17 | `678f373a2e964bf9` |

**为什么 320 和 640 的 FP32 文件是一样大的？** 因为 YOLOv8n 的权重与输入分辨率无关，ONNX 里输入形状是动态的（或是固定但在两种尺寸下参数量相同）。12,077,567 字节 = 12.08 MB 是纯权重+结构，不含激活。这也解释了为什么 `meta.json` 里两个文件的 `size_mb` 都是 12.078。

**六输出 split 的含义**：把原本一个 `[1, 4+nc, 8400]` 的输出拆成 6 个张量：

```
box_s8   box_s16  box_s32      ← 三个尺度的 DFL 回归（reg_max=16 → 4 通道各 16 bin）
cls_s8   cls_s16  cls_s32      ← 三个尺度的 9 类分数
```

拆的原因：RKNN 工具链对"一个输出里混合了不同类型信息"的处理不友好，拆开后每一路都是同质张量，量化阈值可以分别标定。代价是后处理要自己拼（`traffic9_postprocess.py` 是唯一权威实现）。

## 4 · 车道线回归模型：版本谱系与 LOSO 结果

### 4.1 任务定义

输出 4 维：`[锚点 u_ref, 一次项 s, 二次项 q, 有效性 logit]`。
`u_ref` = 参考行（`0.90H = 648 px`）处的车道中心横坐标，解码为 64 箱 softmax 的期望；`s`/`q` 描述形状 `du(t) ≈ s·t + q·t²`，`t = (v − y_ref)/L`。

采样带：7 行固定 `y = 709, 693, 677, 661, 645, 629, 612 px`（纵深 3.40–4.70 m）。

### 4.2 训练数据

`tools/_lane_labels/labels.jsonl`：**296 条，全部 `src="human"`**（0 条 `nolane`、0 条 `human_intent`）。
8 个片段，1 s 步长。`v9` 的划分：**train 222 / val 74**（时间序切分，非随机）。

### 4.3 v9 训练曲线（60 epoch）

|---|---|---|---|---|---|

| 6 | 0.1240 | 71.4 | 42.2 | 243.5 | 72.3 |

### 4.5 四步消融阶梯（这组数字里有两个是无效的）

阶梯定义（`--causal-stack` / `--flip-aug` / `--tail-weight` 三个开关）：

| Step 1 | + 因果窗口（只看过去） | 42.6 | 25.4 | 41.8 | 25.7 |
| Step 2 | + 左右翻转增广 | **42.0** | 23.0 | — | — |
| Step 3 | + 尾部重加权 2.5 | **39.8** | 21.8 | — | — |

**⚠ 两个已知无效的运行，保留在磁盘上但不得引用：**

| run | mean | 状态 |
|---|---|---|
| `step2_flip_clean` | 53.4 | **无效** —— 跑的时候源视频被清理，全程读黑帧 |
| `step3_tail` | 53.7 | **无效** —— 同上 |
| `step2_flip_CONTAMINATED` | 41.1 | **无效** —— 两个进程同时写同一目录，权重文件被交叉覆盖 |

**读法**：四项指标（mean / p50 / p90 / 点 MAE）在种子 0 上单调递减，但**种子 1 上 Step 0→1 是反向的（38.4 → 41.8）**。所以：
- 「因果窗口」这一步**没有证据支持它有益**（一个种子变好 0、一个种子变差 3.4）；
- 「翻转增广」和「尾部重加权」只有种子 0，**n=1，分不出显著性是模型效应还是种子噪声**。

**这是本项工作里我没有做完的部分**，如实记录。

### 4.6 确定性实验（为什么不能用单次运行下结论）

同配置、同种子、**同时**跑两遍（`detA` / `detB`），三折的 `lanenet.pt` **SHA256 全部不同**，但预测几乎一致：

| 指标 | 值 |
|---|---|
| 83 帧逐帧 `pred_offset_px` 差 | mean 0.195 / p50 0.147 / **max 0.505 px** |

结论：**同会话内可复现（差 < 0.5 px），跨会话不可复现**。原因是 `torch.manual_seed` 只设了 CPU 种子，没有设 CUDA 种子，且 cudnn 非确定性算法在不同进程里初始化不同。

后补的 `det1` / `solo` / `rep1..3` 是更早一轮的 22 帧小样本测试，`det/detA/detB` 的 131 帧也是子集 —— **都不是完整 LOSO，别把 65.1 / 53.6 当成模型精度**。

| Windows（原生） | 29.0 | 2.1 | 16.9 | 15.30 |
| WSL2 · `/mnt/d`（9p 文件系统） | 37.0 | 1.7 | 21.0 | 12.14 |

WSL2 的检测反而更慢（37.0 vs 29.0）——**不是 CPU 慢，是 9p 文件系统读视频慢**。做了对照实验：

| 配置 | 帧数 | 墙钟 | FPS |
|---|---|---|---|
| 视频与输出都在 `/mnt/d`（9p） | 599 | 55.5 s | **10.79** |
| 视频与输出都在 `/tmp`（ext4） | 599 | 49.1 s | **12.20** |

**9p 吃掉 13%。** 结论：WSL 里跑要把视频先拷到 `/tmp`。

## 6 · 车道线置信度标定

### 6.1 问题

有效性 logit 的目标恒为 1.0（296 条全是正样本），`sigmoid(logit)` 恒等于 **1.000**，方差全是浮点噪声。300 帧实测 `conf` min/p50/max = 0.9933 / 0.9984 / 0.9984，**std 0.0019** —— 这是个常数。

### 6.2 找出唯一有信号的量

对 296 帧 LOSO 误差与运行时特征做 Spearman 秩相关：

| 特征 | rho | 判定 |
|---|---|---|
| `abs_anchor`（模型自报 \|锚点\|） | **+0.359** | 有效 |
| `abs_s`（一次项） | +0.319 | 有效 |
| `abs_q`（二次项） | +0.216 | 弱 |
| `logit`（原"置信度"） | −0.138 | 无 |
| `paint_cov_band`（漆线覆盖率） | −0.011 | 无 |
| `paint_cov_ctr` | −0.013 | 无 |
| `lum_mean` / `lum_std` / `grad` | −0.062 / −0.100 / −0.040 | 无 |
| `n_veh_band` / `veh_w_frac` | −0.060 / +0.018 | 无 |

**漆线覆盖率和误差完全不相关** —— 这条推翻了我原本"标线不清晰所以不可信"的假设。

### 6.3 最终标定式

```
expected_ae_px = expm1(b0 + b1 · min(|anchor|, 0.0760))
AE_CALIB = (2.766376, 11.879325)      # b0, b1
AE_FULL_SCALE = 150.0
confidence = clip(1 − expected_ae/150, 0.02, 0.98)
```

LOSO 评估：`rho = 0.1708`，`|预期误差 − 实际误差|` 中位数 = **15.17 px**。

**这个 rho 只有 0.17，等于说标定很弱。** 它的价值只在高误差那一端 —— 十分位最差的一档，预期误差能从"全体中位 22.8 px"抬到"这一档实际 55+ px"。

**截断的必要性**：不加 `min(·, 0.0760)` 时，一帧 `|anchor| = 0.247`（大幅左偏，全量模型其实预测得很准，误差仅 5.6 px）会被算成预期误差 284.9 px、置信度 0.02、直接判为 `valid=False`。截断把预期误差上限压到约 38.8 px、置信度下限约 0.74。

### 6.4 标定后实测（`conffull`，959 帧）

| 指标 | 值 |
|---|---|
| 有效帧 | 957 / 959 = 99.8% |
| `conf` min / p5 / p50 / max | 0.741 / 0.762 / 0.886 / 0.901 |
| `conf` std | 0.028 |

不再是常数，但**动态范围只有 0.16**，可视上几乎看不出变化。这是标定强度不足的直接后果，不是渲染问题。

### 7.4 QDQ 数值等价性

`rknn_export_report.json`（8 张夜间图）：

| 指标 | 最差值 |
|---|---|
| `split_qdq_vs_ref_max_abs` | 1.22e-4 |
| `split_qdq_vs_ref_mean_abs` | 约 3.8e-6 |
| **`fp32_vs_qdq_max_abs`（框坐标 px）** | **305.69 px** |
| `worst_fp32_vs_qdq_score` | 0.4448 |

**这里有个必须解释清楚的现象**：拆成六输出的 QDQ 模型与参考的 QDQ 模型**数值完全等价**（1.2e-4 是浮点表示误差），但**它和 FP32 模型的框差到 305 px**。

原因：FP32 模型是 `verified_20260915` 之前的另一份权重导出的，**两者根本不是同一个模型**。`worst_fp32_vs_ref` 和 `worst_fp32_vs_qdq` 都是 305.69 px —— 说明差异全部来自权重版本，不来自拆分或量化。**这个 305 px 不能用来评价量化损失。**

### 10.5 结论与限制

- **单路**：RK3568 NPU + 前后处理约 **47 ms/帧**（n=100）；15 fps 链能跟上，
  150 帧 0 丢帧、0 等待超时。
- **双推理**：两路合计约 **106 ms/帧**；文件源 6.79 fps，UVC 链 5.74 fps。
  双推理的代价是板端帧率从 15 fps 降到约 5.7 fps，PC UI 仍约 15 fps。
- **没有端到端玻璃到玻璃延迟**：板端计时从预处理开始，到后处理结束；不含 HDMI
  输入/采集卡/JPEG/UDP/PC 显示。没有 Frame Marker，也不能声明严格同帧或 LIVE。
- **没有板端视频 mAP**：只有 129 张静态 val 的量化精度；四宫格整帧检测数不能当
  四路准确率指标（FPGA 下排是车内视角）。
- UVC 链的日志每 10 帧一行（n=16/10），**P95 只能当参考，不是 P99**；文件源
  n=100 的 P95/P99 也只代表这 100 帧、这个模型和这个场景。
- 写表时采集卡未插在板上，未重跑 UVC；若要更新 UVC 数据，先接回
  `/dev/video0` 再按 §10.4 的命令重跑。
