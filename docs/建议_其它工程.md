## 一、协议头：CRC-16 要不要加

### 1.1 现状（先把地基说清）

| 项 | 值 |
|---|---|
| magic | `0x5954`（"YT"） |
| 协议版本 | v1，little-endian |
| 公共头 | **40 字节**，全部字段自然对齐 |
| CRC | `zlib.crc32(header[0:36] ++ payload)`，标准多项式 `0xEDB88320`（反射式，即 `0x04C11DB7`） |
| CRC 位置 | 偏移 36，**头的最后一个字段** |
| `payload_length` | uint16，上限 65535，超长必须分片 |
| 分片 | `fragment_index` u8（偏移 29）、`fragment_count` u8（偏移 30） |

### 1.2 结论：**位置对，但默认不该加**

**你问的是"帧头要不要加 CRC-16/CCITT，放在 payload 前面"。**

**位置是对的**——放 payload 前面（也就是头的末尾）正是正确位置，因为只有这样它才能覆盖整个头。

**但"要不要加"要分两件事看**：

- **它不是"数据完整性"**。CRC-32 已经覆盖 `header[0:36] ++ payload`，全部字节都在保护范围内。再加一个覆盖同样字节的 CRC-16，是重复校验同一段数据。
- **它是"头可信性"**。CRC-32 有一个固有缺陷：**必须读满 `payload_length` 字节才能验**。如果 `payload_length` 这个字段本身被打脏（比如 `0x0064` 变成 `0xEA60` = 60000），接收端会白读 60000 字节才失败，期间还要占着缓冲。CRC-16 能在读满 40 字节时就判定"头不可信，别信这个长度"。

**所以判断依据是传输层**：

| 传输层 | 加不加 | 理由 |
|---|---|---|
| **UDP over 千兆网**（本方案主线） | **不加** | datagram 边界已经隐含校验了长度：实际包长 ≠ 40 + `payload_length` 立即就能看出来，不需要额外校验 |
| **裸流**（AXI-Stream / SPI / UART / HDMI 嵌入 / SFP 直连） | **加** | 没有边界，长度字段被污染就会一路错到底 |

**方案主线是 UDP（`192.168.50.0/24` 千兆交换机），所以默认答案是"不加"。** 但你们还有 2 × SFP HSST 支线（3.1875 / 6.375 Gbps）——如果将来走那条路，CRC-16 就该加。

### 1.3 如果决定要加：零破坏改法

**不要改头长度，不要改任何现有字段的偏移。** `header_reserved` 是 `uint8[4]`（偏移 32，原文写"必须写 0，接收端忽略"）——拿它的最后两个字节。

```text
偏移  字段                 现状                              建议
  0   magic u16            0x5954                            不变
  2   protocol_version u16 1                                 不变
  4   frame_id u32         —                                 不变
  8   timestamp_ns u64     —                                 不变
 16   sequence u32         —                                 不变
 20   calibration_id u16   —                                 不变
 22   payload_length u16   —                                 不变
 24   message_type u8      —                                 不变
 25   source_id u8         —                                 不变
 26   mode_id u8           —                                 不变（但语义有缺口，见 §2）
 27   status u8            —                                 不变
 28   invalid_reason u8    —                                 不变
 29   fragment_index u8    —                                 不变
 30   fragment_count u8    —                                 不变
 31   clock_domain_id u8   —                                 不变
 32   header_reserved[4]   必须写 0                          header_reserved[2] + crc16 u16 @34
 36   crc32 u32            header[0:36] ++ payload            不变

头长仍为 40 字节。
crc16 = CRC-16/CCITT-FALSE (poly 0x1021, init 0xFFFF)，覆盖 header[0:34]。
```

### 1.4 加之前必须先说清的三件事

1. **名字要叫对**。你要的是"**头** CRC-16"，不是"**帧** CRC-16"。一旦叫成帧 CRC-16，实现的人就会拿它去覆盖 payload——那就真成了双重校验，白花两个字节和一级状态机。
2. **CRC-32 的覆盖范围要重新界定**。现在是 `header[0:36] ++ payload`，`crc16` 自己也算在内——这没问题（只多一次查表），但**不能因为有了 CRC-16 就丢 CRC-32**。CRC-16 漏检率是 1/65536，CRC-32 是 1/4.3×10⁹，差五个数量级。视频帧里一个 16 位都查不出的错误，CRC-32 能查出来。
3. **如果真实需求是"边收边验"**（FPGA 里 payload 直接进 DMA，等最后一字节才知道对不对），正确的做法是**增量 CRC-32**：CRC-32 可以逐字节推进（查表），头部 36 字节到达时就开始算，payload 流入 DMA 的同时并行推进，最后一字节到达时立即比对。**延迟和 CRC-16 一样，而且不需要第二个校验器。**

## 二、`payload_length` 用 2 字节：**合理，不用改**

### 2.1 结论

uint16 上限 65535，与 IPv4 总长同款，是这个场景的标准选择。而且分片字段已经在协议里（`fragment_index` / `fragment_count`），超长消息本来就要分片——所以 2 字节不会成为任何东西的瓶颈。

### 2.2 唯一要算的账在分片计数，不在长度

| 分辨率/格式 | 一帧字节 | 需分片数（每片 65535） | uint8 上限 255 |
|---|---:|---:|---|
| 720p RGB565 | 1,843,200 | 29 | 宽裕 |
| **1080p RGB565** | **4,147,200** | **64** | 宽裕 |
| 1080p BGR888 | 6,220,800 | 95 | 宽裕 |
| **4K RGB565** | **16,588,800** | **254** | **几乎顶满** |

**结论：1080p30 完全没问题；上 4K 时 `fragment_count` 的 8 bit 就没有余量了。** 你们现在跑 1080p30，不用管；但这条要写进"已知限制"，否则将来上 4K 会发现分片数溢出，而症状是"偶尔拼出一帧乱码"——极难定位。

## 三、`mode_id` 的语义缺口（**这份文件里最重要的一条**）

### 3.1 问题

`enums.json` 里：

```json
"source_id": { "PANGU50K": 0, "P100PRO_PLUS": 1, "RK3568": 2, "PC": 3, "UNKNOWN": 255 }
```

而 `mode_id` 在 `PROTOCOL_FIELDS.md` 里的说明是 `0=camera, 1=fusion, 2=enhance`——**这是图像处理模式，不是视频来源模式**。

你现在有三种视频模式（四路内录 / 两实时+两内录 / 单或两路）。**协议里没有任何字段能表达"这一帧哪几格是实时、哪几格是回放"**：

- `source_id` 是**板级**的，不是相机级的；
- `invalid_reason` 里有个 `REPLAY_EOF`(22)，但那是错误码——回放是常态，不能用错误码表达常态；
- `roi_relation` 是车道关系（EGO/LEFT/RIGHT/UNKNOWN），与相机无关。

### 3.2 后果

PC 端没有任何依据去分格标注。四路界面会看起来**全部是实时的**——而其中两格可能是几秒甚至几十秒前的录播。

这是"展示与真实不一致"里最难解释的一类：**画面本身没有错，错在你没有说它是什么**。事后没人能证明当时那两格是回放，也没人能证明不是。

RK 端更严重：它是决策点，会拿"两格是录播"的画面跑 ADAS 规则，在不存在的场景上判定告警。

### 3.3 建议（最小改动）

优先用 `CTRL` 扩展，不动公共头：

```text
CTRL (0x01) 追加一字节
  source_map  uint8    bit i = 1 表示相机 i 为实时，0 表示回放
                       位序：bit0=F(前) bit1=B(后) bit2=L(左) bit3=R(右) bit4~7 保留=0
```

同时 `HEALTH` 里回带上行**实际生效**的 `source_map`（防止设置失败但没人发现）。

**判据**：PC 仅凭报文就能还原"这一帧哪几格是实时"，且界面上按格显示 `LIVE` / `REPLAY`。

## 四、几何与拼接（跨板约定）

### 4.1 拼接必须是**不重叠 2×2 宫格**

**理由**：不重叠时，每一格与原相机图像的映射是"纯平移 + 等比缩放"，一个 3×3 单应矩阵就够，**而且逆变换永远存在**。一旦做了重叠羽化，重叠区的像素是两路加权和，逆变换不再唯一——下游（RK 的 YOLO 要反变换回 1280×720、PC 的 3D 要反投影到地面）全部失去几何前提。

**判据**：任取一格，用 4 对点解单应矩阵，验证它退化为纯缩放+平移（残余透视项 < 1e-6）。

### 4.2 `Frame Marker` 必须在**第 0 行**，且四格共用一个 `frame_id`

**依据**：三板接口方案 §2.1「连续纯净视频帧（顶部第 0 行嵌 `Frame Marker`）」。

**为什么要写进第 0 行而不是走独立消息**：视频和元数据走的是两条完全不同的物理链路（HDMI vs 千兆网），只有把帧号**钉在像素里**，才能保证"我拿到的是哪一帧"不依赖任何网络时序。这是整条链做 `frame_id` 对齐的唯一物理锚点。

**判据**：任取一张宫格，四格解码出的 `frame_id` 相同；连续两帧差 1。

## 五、单位与口径（曾出过错的地方）

### 5.1 一律 SI：1 MB = 10⁶ B

方案 §1.5 记录了这个坑：母报告把「940 Mbps ≈ 112.5 MB/s」判为错误，实际 **940 Mbps = 117.5 MB/s = 112.1 MiB/s**——两种口径都对，但混用就错。**本项目一律 SI。**

### 5.2 曲率写 `1/px`，不写 `1/m`

单目没有标定就没有米制曲率。`lane_predict.py` 返回的键名就是 `curvature_px_inv`，**这不是笔误，是刻意的**。

### 5.3 置信度未标定时叫 `score`，不叫概率

`PGL50H子方案.md:445` 明确要求「不得在未校准前声称概率」。当前 `lane_predict.py` 输出的 `confidence` 是**标定后的期望误差**（`AE_CALIB`），不是概率——界面上必须写明这一点。

### 5.4 `source ∈ {REPLAY, LIVE, SIM}` 横幅常驻

这不是装饰。一份演示视频如果没标源，事后无法区分"这是回放"和"这是实时"。**任何时刻都必须在画面上。**

## 六、工程纪律（我自己踩过的）

### 6.1 状态灯恒绿是已知反例

`tools\adas_dash.py:220` 有一行：

```python
(("detect", True), ("track", True), ("lane", True))
```

**三个 `True` 是写死的**。这盏灯永远绿，不管实际有没有在跑。新写的任何面板不要重复这个错误——状态必须来自实际计数（`frame_id` 是否在推进、`valid_ratio` 是否 > 0、`TIMING` 是否在更新）。

### 6.2 不要把"条件成立时才有效"的判据当成通用判据

这一条是我在这个项目里反复犯的同一类错误，共四次：
- 用"`v` 单调递增"判断车道线有效 → 弯道和遮挡时失效；
- 用"折返度"判断左右转方向 → 远场测的是相机横滚，不是航向；
- 用"意图标注"否定转向帧 → 三个理由全被推翻，标注已全部还原；
- 用"A/B 分组"证明左偏样本缺失 → 每折留出的片段不同，分组逻辑本身不成立。

**共同形状：把一个只在特定条件下成立的模型，提升成了通用判据。** 写判据前先问一句"这个判据不成立时，会表现成什么样"。

### 6.3 `tests_pass` / `rms` / `shape_ok` 这类"构造上恒真"的检查不算检查

V3 的 7 个采样点是由网络输出的 `(s,q)` **重建**出来的，按构造落在二次曲线上——所以 `np.polyfit` 残差恒为浮点噪声（实测 300 帧 `rms` min/p50/max 全 0.00）。**一个恒真的检查项比没有检查更糟**，因为它会让人以为验过了。

## 七、需要你确认的四件事

1. **SFP HSST 支线会不会真的用来传视频？** 会 → CRC-16 该加；不会（只是通信专项验证）→ 不加。
2. **`CTRL.source_map` 是我按最简方案提的，你更想要独立消息还是在公共头加字段？** 公共头加字段要改 40 字节布局，影响面大；`CTRL` 扩展不动别人。
3. **`ROADTHUMB` 的 `scale/pad` 参数在协议里到底有没有？** 母方案 §2.4 说携带，但我在 `protocol_schema\` 里没找到。如果没有，RK 侧"反变换回 1280×720"就无法实现。
4. **`Frame Marker` 的具体编码定了吗？** 第 0 行 1920 个像素怎么放 32 位 `frame_id` + 校验？这决定三个板子的实现能不能对齐。

## 八、一句话总结

**这份文件里唯一"现在不改、后面一定返工"的是 `source_map`（§3）。** CRC-16 和分片计数都可以等实测再定，但"这一帧哪几格是回放"这件事，一旦各板按"全是实时"写完了再补，就是全链路返工——而且补上之后你会发现，所有已经录好的演示素材都没法补标注。
