## 硬约束（违反任何一条，这次交付就算废）

1. **不产生任何测量值。** 你不跑检测、不跑跟踪、不跑推理。画面上每一个数字都必须来自收包字段或由它们确定性算出。
2. **禁止写死常量。** 不许出现 `FPS: 30`、`延迟: 25ms`、`system_mode = FULL` 这种写死的展示值。
   现有 `tools\adas_dash.py:220` 就有反例（`(("detect", True), ("track", True), ...)` 状态灯恒绿），**不要重复这个错误**。
3. **不可用就明写。** 任何字段缺数据时显示 `— unavailable (REASON_CODE)`，**不显示 0，不显示上一帧的值**。
   必需的原因码至少包括：`NO_VIDEO`、`NO_TRACK`、`NO_LANE`、`NO_MOTION`、`CALIB_MISSING`、`FRAME_MISMATCH`、`LINK_DOWN`。
4. **标定缺失必须降级，不许假装。** 没有实测外参时，`calib_flag = RELATIVE_HOMOGRAPHY`，
   所有米制量（距离、速度、TTC）一律 `unavailable`，只报像素/相对量。**这条是母方案的红线。**
5. **单位标注要对。** 图像平面曲率写 `1/px` 不写 `1/m`；置信度在未校准时叫 `score` 不叫概率。
6. **`frame_id` 是唯一关联主键。** 视频纹理与感知报文必须在滑动窗口内按 `frame_id` 严格配对；
   配对不上就丢这一帧并计数 `frame_mismatch_cnt`，**不许用"到达时间相近"代替**。
7. **不做车辆控制。** 不输出转向/油门/刹车指令，不做碰撞倒计时，不接任何执行器。

## 外部数据契约（板端还没做，你必须自己造测试数据）

板端目前不存在，所以**你必须提供两个东西让整个模块能独立跑起来**：

1. **一个四路合帧的视频源**：可以是拼接好的 `1920×1080` mp4（左上=前、右上=后、左下=左、右下=右，
   每路 `960×540`），也可以是分目录的四路 mp4。允许用**同一段单目素材复制四份**先跑通管线，
   但**必须在界面上标注 `source = SIM` 并常驻显示「模拟四路，非真实环视」**。
2. **一个报文回放器**：从 JSON/CSV 读 `LANE`/`MOTION`/`OBJECT`/`TRACK_V1`/`HEALTH`/`TIMING`，
   按真实频率推到 UDP 本地回环。**这是唯一的验收输入方式**，不许依赖真板。

`TRACK_V1` 的单条目标结构（来自评审方案 §4，**照抄，不要自己改字段名**）：

```c
struct TrackItemV1_AVM {
    uint32_t track_id;          // [31:24]=cam_id(0:F,1:B,2:L,3:R), [23:16]=class_id, [15:0]=local_id
    uint8_t  cam_id;            // 0=Front, 1=Rear, 2=Left, 3=Right
    uint8_t  class_id;          // 0=car, 1=person, 2=light, 3=sign, 4=truck, 5=bus, 6=moto, 7=bike, 8=other
    uint8_t  state;             // 0=TENTATIVE(虚线), 1=TRACKED/CONFIRMED(实线), 2=LOST(仅预测)
    uint8_t  observation;       // 0=DETECTION(当帧真实检出), 1=PREDICTION(外推)
    uint16_t score_q10;         // score * 1000
    uint16_t bbox_sub_xyxy[4];  // 所属相机 960×540 原图下的 2D 框

    int16_t  car_y_cm;          // 车体系右向地面坐标（车右为正）
    int16_t  car_vx_cms;
    int16_t  car_vy_cms;
    uint16_t foot_width_cm;
    uint8_t  roi_relation;      // 0=IN_EGO_LANE, 1=BLIND_SPOT_NEAR(<3m), 2=SURROUND_NORMAL
    uint8_t  calib_flag;        // 0=UNINITIALIZED, 1=RELATIVE_HOMOGRAPHY, 2=METRIC_CALIBRATED
```

- 不接 HDMI 采集卡也能跑（用 mp4），但接口要留好

## 报告纪律

- 任何"跑通了"必须有原始输出或截图；没跑过的不写成跑过
- 性能数字必须给 P50/P95 和测量条件（分辨率、GPU 型号、是否窗口化）
- 做不到的写在"已知限制"，**不要悄悄降级**
- 若发现需求本身有矛盾（比如评审方案要 GPU 实时反投影，但母方案 §9.5 选的是 CPU 版 PySide6），

# 第三部分 · 关于四路环视的补充建议（针对已上板的实际条件）

> 前面的 WBS 和提示词是在"板端还不存在"的假设下写的。现在 50K 已经能输出不重叠 2×2 宫格、
> 且已有三种视频模式（四路内录 / 两实时+两内录 / 单或两路）。**这一部分是对前述内容的修正和补强**，
> 若与前文冲突，以本部分为准。

## S-1 · 纹理源：用板端拼好的宫格，**不要另开一路本地素材**

**结论**：`TextureSource` 的主实现应该是"接收板端输出的 1920×1080 宫格"（HDMI 采集卡或 UDP），
而不是"自己打开一个本地四路视频文件"。

**理由**：这一条之前写反过，现在修正。原先担心"处理后的视频几何被破坏"，那是针对**碗状/柱面投影**说的。
你实际实现的是**不重叠 2×2 宫格**——每一格和原相机图像之间是"纯平移 + 等比缩放"，
一个 3×3 单应矩阵就够，而且逆变换永远存在。所以**宫格完全可以用作纹理**，几何一点没丢。

**真正的理由是另一条**：如果纹理来自本地视频文件、而叠加层来自板端实时推理，两者就是**两段不同的画面**。
这不是"延迟 100 ms"能描述的问题——延迟至少还是同一段路。必须让纹理和叠加来自同一条链路。

## S-2 · 混合源（两实时 + 两内录）必须**分格**标注

**结论**：四格里哪几格是实时、哪几格是回放，必须在画面上逐格显示，不能只给一个全局 `source` 横幅。

**理由**：`mode_id` 在协议里是 `0=camera/1=fusion/2=enhance`（图像处理模式），
**没有字段表达视频来源**；`source_id` 是板级的，`invalid_reason` 里的 `REPLAY_EOF` 是错误码不是常态属性。
也就是说：**PC 端现在拿不到"这一帧哪几格是实时"这个信息。**

在协议补上 `CTRL.source_map`（每相机 1 bit，0=replay 1=live）之前，这一层只能靠外部配置硬编码，
并且**必须在界面上写明"source 分辨率来自配置，非报文"**——不许假装它是从数据里读出来的。

## S-3 · `frame_id` 回放：等第 N 帧的叠加回来，再显示第 N 帧

**结论**：不许"显示最新画面 + 画稍早的叠加"。

**理由**：板端链路有 100~150 ms 的延迟。如果 PC 显示本地最新帧、却把 150 ms 前的叠加画上去，
在 30 km/h 下框会**系统性地偏后约 1 m**，而这个偏移看起来完全正常——你不会觉得框飘了，只会觉得"检测有点保守"。
这是最难自查的一类错误。

**做法**：PC 维护一个 `frame_id` 索引的帧缓冲（约 300 ms 深），收到第 N 帧的叠加才取出第 N 帧纹理显示。
代价是画面整体滞后，但内部自洽。**滞后是可接受的，"对不上"不可接受。**

## S-4 · 采集点必须在 50K 或 100Pro+ 的 HDMI OUT

**结论**：不要从 RK3568 的 HDMI OUT 采集。

**理由**：RK 是最终出图那一级，它的 HDMI OUT 上已经烤进了 2D 叠加（框、车道、面板）。
PC 从这里采集再叠一层 3D，就是**双重叠加**：旧框会成为背景纹理的一部分永久留在画面上，
新框画在同一位置附近，形成"框跟着框"的鬼影。

**判据**：关闭 RK 叠加前后，PC 收到的纹理应**完全一致**。

## S-5 · 碗状投影留在 GPU，不要指望板端做

**结论**：`A3D-05/06` 的碗状地形与四相机羽化混合，全部在 PC 的 fragment shader 里实时算。

**理由**（把账算清）：
- 不重叠宫格里每格是纯缩放，所以**技术上** 100Pro+ 用 line buffer 就能做流式 remap；
- **但** 4 相机 × 64 行 × 960 px × 2 B ≈ 480 KiB，而 100Pro+ 总 DRM 只有 697.5 KiB，
  光流主线已经吃掉大头，`SAT-PG100-RESOURCE` 还要求 DRM ≤ 52%；
- 更关键的是**做完视角就固定了**，不能拖拽；而 PC GPU 做同一件事是免费且可交互的。

**所以**：不是"FPGA 做不了"，是"用 480 KiB DRM 换一个不能拖拽的固定视角，不如把这 480 KiB 留给光流的行缓存"。

## S-6 · `A3D-03` 的"冻结四宫格 mp4 回放"仍然是必需的

**结论**：即使有了 HDMI 采集卡，mp4 回放这条实现也要保留。

**理由**：它是唯一能在**没有板子**的情况下跑通整条链路的输入源。
板子不在手上时的调试、CI、以及给别人演示，都靠它。但要遵守两条：

1. 用同一段单目素材复制四份时，**必须常驻标注 `source = SIM`** 和「模拟四路，非真实环视」；
2. 宫格必须是**不重叠 2×2**（每格 960×540），不能为了"看着连贯"而做羽化——理由同 S-1。

## S-7 · 这一部分不要在代码里留下"以后再说"的口子

具体指：`source_map` 缺失时，**不许默认成"全部实时"**。默认成 `UNKNOWN` 并在画面上标 `SOURCE_UNKNOWN`，
比默认成 `LIVE` 好得多——因为前者会让人去查，后者不会。

（这与前文硬约束第 3 条「不可用就明写」是同一条规则的延伸。）
