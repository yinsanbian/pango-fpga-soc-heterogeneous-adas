# PG100 HDMI RX 调试更新（阶段 2 观测结果）

- 日期：2026-11-03 20:30
- 当前位流（20:20 原子快照版）：SHA256 `1b8b4faf71205b29fd41cb53db7aa59f38a65562907186eeae445e934e38da53`
- 上一版（20:05 原始 RX 计数版）：已被覆盖，**未记录 SHA256**（流程违规，如实记录）
- 50K 位流不变：`video_n1_uart_burst8.sbit`，SHA256 `63dd3e1610e255c6330bf3cf5cf2b30651aea2fe292b7f05286cce39b11da498`

## 1. 关键新证据：RX 输入是合法的 1080p60

20:05 版在 `rx_pclk` 域直接统计 `rx_vs/rx_hs/rx_de` 上升沿（1s 快照，经 toggle 握手）：

| 计数 | 实测增量 | 理论值（1080p60 CEA） | 判定 |
|---|---|---|---|
| `rx_vs_cnt` | ≈60 /s | 60 | 正常 |
| `rx_hs_cnt` | ≈67,500 /s | 67,500 | 正常 |
| `rx_de_cnt` | ≈64,800 /s | 64,800 | 正常 |
| `rx_de_high` | ≈124.4M /s | 148.5M×83.8% ≈ 124.4M | 正常 |
| `vs_cap`（capture 域） | ≈60 /s | 60 | 正常 |

结论：**MS7200 正在向 FPGA 输出有效 VS/HS/DE，帧率/行率/DE 占空比与 1080p60 完全一致。** 之前“无信号/RX 未锁”的判断不成立。

同一版本下 `0x209E` 读回 `0x00`、`freq_tries=99`、强制使能。**说明官方 `freq_ensure` 使用的频率寄存器在我们的配置/读取方式下是假阴性，不能作为锁定判据。** 原始 DE/HS/VS 计数才是可靠证据。

## 2. 采集仍丢帧，但原因数据被跨域撕裂

20:05 版读数（同一时段）：

```
fc = 50,167 / 0 / 377,847（交替）   al = 1080
cap = 0, disc 约 30/s 增长
commit_reason = 0, bad_reason = 0, bad_frame = 0
good = 0, bad 随 disc 增长
```

- `fc=50,167` 与 `al=1080` 不可能来自同一帧（1080 行至少约 2.37M 周期），说明 `w32/w33/w37` 这些 pclk 域多位信号直接进 native 快照时被撕裂。
- `commit_reason=0`、`bad_frame=0` 但仍在丢帧，同样是不可信读数。
- `bad_identity` 与 `discarded` 同步增长，说明每个 frame_end 都被 bridge 判为 `pending_good=0` 或身份无效；但具体原因需可靠快照。

## 3. 时序报告：违例全部是调试总线跨域

`prj_tasks/pnr_1/report_timing/pg100_mainline_board_top.rtr`：

- 违例路径的起点是 `hdmi/dbg_rx_vs_cnt[*]`、`hdmi/dbg_rx_de_high[*]`、`hdmi/config_owner/dbg_freq_value[*]`；
- 终点是 `local_control/snapshot/held_native[...]`；
- 路径组 `ddrphy_sysclk`（native），例如：
  - `dbg_rx_vs_cnt[4] -> held_native[932]`：Setup Slack **-0.338 ns**
  - `dbg_rx_de_high[18] -> held_native[114]`：Hold Slack **-2.367 ns**
- `hdmi_pclk` 时钟本身：估计 166.06MHz / 请求 148.5MHz，估算裕量 **+0.712 ns（MET）**。
- 结论：当前诊断版的负裕量来自**未同步的多位调试总线**，不是 pclk 内部逻辑；但这会污染读数（与第 2 节撕裂一致）。

## 4. 20:20 原子快照版的反常

- 把 capture 的 `fc/al/cap/disc/reason/overflow` 与原始 `vs/hs/de` 一起在 pclk 域锁存、握手到 clk27 后：
  - `de`、`de_high` 仍然正确（≈64.8k/s、≈124.4M/s）；
  - `vs=0`、`hs≈30/s`（应为 60/s、67.5k/s）；
  - `vs_cap=0`、`cap=disc=0`。
- 同一 pclk 块内 `de` 正确而 `vs/hs` 错误，说明 vs/hs 的边沿检测/寄存器在本次布局 seed 下再次被改坏（与之前 `vrise` 被提升同类风险）。
- 该版不能用于结论；需要先做时序干净、结构稳定的最小诊断版。

## 5. 颜色问题（新增线索）

- 用户确认 50K 直出画面颜色正常（附图：2×2 拼屏、顶部 PGM1 条带、颜色正确）。
- 100Pro 直通在不同构建下出现过**偏绿**（17:22 版）和**偏红**（20:05 版附近）的整屏色偏；同一源、同一 50K。
- 检查 FDC：只有 `create_clock hdmi_pclk`，**没有对 `hd_rx_rgb/hs/vs/de` 的 `set_input_delay`**；官方 `2_10_hdmi_loop` 的 FDC 也没有输入延时约束，而且其 EDID 是 1080p30-only、示例按 74.25MHz 运行。
- 当前 50K 输出是 1080p60（148.5MHz），RX 并行总线的速率是官方示例的 2 倍。缺少输入延时约束时，24 位数据相对 pclk 的板级 setup/hold 未被时序分析覆盖，布局 seed 变化会改变哪一位出错——与“偏绿/偏红随构建变化”高度吻合。
- 这属于独立的显示/像素总线问题，与采集判据分开处理。

## 6. 下一步建议（按优先级）

1. **先做时序干净的诊断版**：去掉/隔离调试总线（pclk 域多位信号必须经握手或原子快照后再进 native；在 FDC 中只对已证明的异步调试路径设置例外，并逐条记录理由），目标 `WNS>=0、TNS=0`。在干净版上复测颜色与采集。
2. **给 RX 并行总线加输入时序约束**：依据 MS7200 数据手册的输出延时/板级走线，添加 `set_input_delay`（pclk 相对）；没有手册时先用保守估计做实验，不要凭空声明通过。也可用 1080p30 源做对照，验证“总线速率”假设。
3. **频率门槛降级为遥测**：`0x209E` 在实测中为 0 但视频有效，不应作为使能门禁；保留读取值/重试次数，不再阻塞初始化。
4. **恢复可信的采集判据**：在干净版上只保留必要的最小遥测（pclk 域锁存 + 握手），重新读 `commit_reason/bad_reason`，再决定提交窗口或 PGM1 适配。
5. **版本管理**：每次构建先记录 SHA256；把 08:25 成功版的源码/位流恢复列为独立任务（当前位流已丢失）。

## 7. 与假设的对照（更新）

| 假设 | 判定 | 证据 |
|---|---|---|
| H1（RX 未复位/初始化竞争） | 部分不支持 | G25 每配置复位 100ms；原始 DE/HS/VS 正常 |
| H2（配置不完整/频率校验） | 不成立为主因 | `0x209E=0` 但视频同步完全正常，频率门禁是假阴性 |
| H3（FPGA pclk 域逻辑/时序） | **支持** | 违例集中在调试跨域；vs/hs 计数在换 seed 后异常；颜色随构建变化 |
| H4（TX 未初始化） | 未证明 | 直通有画面（颜色异常），TX 基本工作 |
| H5（HS/VS 边沿 CDC/综合） | **支持（与 H3 同源）** | 同一 pclk 块内 de 正确、vs/hs 在 20:20 版异常；历史上 vrise 被提升 |
